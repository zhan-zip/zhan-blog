## 如果你只能给一个 Agent 系统增加一项能力——更强的模型、更丰富的上下文还是更多的工具——你会选哪个？在什么条件下你的选择会改变？

我觉得应该分情况讨论，如果需要增加的功能是类似于获取时间、分析某个指定类型的数据、执行某个特定任务的话，这种功能和其他方面耦合度较低，不是很复杂，可以自己实现，同时又不能通过升级模型来实现的话，可以增加新的工具；如果是使Agent在执行任务的过程中增加某个功能，类似于“在完成任务后进行测试”“执行之前先制定计划”，那么写进上下文或提示词比较好；如果是通过升级模型即可获取的功能，比如生成图片、生成语音等，换一个底层LLM比较好。

补充：这里问的是“更丰富的上下文”，不是“提示词”。上下文通常指模型能看到的信息，比如历史、检索结果、工具返回；提示词更像指令和规则。

* 更好的判断方式是先找**瓶颈**：

  * 模型“不知道” → 加上下文。

  * 模型“不会做” → 换更强模型。

  * 模型“做不到” → 加工具。

- 换模型虽然是“升级”，但成本最高、周期最长，且可能带来不可控的退化（比如新模型在某些特定任务上反而变差）。所以工程上通常是：**优先改上下文，其次加工具，最后才换模型**。

## ReAct 循环中，累计缓存读取量随轮数近似二次方增长。如何降低这种增长？

压缩记忆？对于历史记忆，分为长期记忆和短期记忆，长期记忆进行压缩，仅保留列点式的重点，短期记忆用于保留上下文记忆连贯，当缓存读取量达到某个特定值时进行压缩。

补充：除了压缩，还有几种常见手段：

1. **滑动窗口**：只保留最近 N 轮对话，更早的直接丢弃。
2. **摘要记忆**：让模型定期把历史对话总结成一段摘要，替代原始对话。
3. **向量检索（RAG）**：把历史存入向量数据库，需要时只检索相关片段，而不是全量塞入上下文。
4. **KV Cache 优化**：在底层推理引擎层面，利用前缀缓存（Prefix Caching）避免重复计算未变化的上下文，这能大幅降低算力成本，但不减少 Token 数量。

* “达到阈值就压缩”需要小心：压缩本身也要消耗 Token 和算力，如果压缩太频繁，可能得不偿失。需要权衡压缩频率和压缩粒度。

## “模型即 Agent”范式意味着模型在工具调用决策上越来越自主。但本章论证了 Harness 工程的重要性反而在增加。这两个趋势如何共存？Agent 框架未来的核心价值体现在哪些方面？

我觉得在AGI真正实现之前，模型的能力依旧需要在特定场景下的指定约束和优化，也可以说是Harness工程和模型的发展是相辅相成而不是互相矛盾的，虽然模型的发展必然会吃掉“脚手架”和“适配层”，但本质上只是内化了可重复可优化的部分Harness，而完整的Harness工程不只有这一部分，更多的是驾驭而不是提供更多功能。我认为就算实现AGI也是在Agent的基础上实现，更何况Agent框架可以在不修改模型的基础上进行相对轻量的任务适配处理，模型越强，Harness工程也越重要。

补充：Harness 未来的核心价值可以具体化为：

* 多 Agent 协作：模型内化的是单 Agent 能力，但多 Agent 之间的通信、协商、任务分配，仍然是 Harness 的职责。

* 安全与权限：能做什么，不能做什么。

* 工具编排：调用顺序、重试、降级。

* 状态与记忆：长任务不丢状态。

* 可观测与评估：知道它为什么失败。

* 成本与延迟：控制预算。

* 合规与审计：生产环境必须可追溯。

* 人机协作：何时移交给人。

所以两个趋势不矛盾：模型内化“能力”，Harness 定义“边界”和“责任”。

## 消融实验中“工具结果反馈”的缺失会让 Agent 反复重试直到耗尽迭代预算。在生产环境中，除了工具结果缺失，还有哪些情况可能让 Agent 陷入这种循环？你会设计怎样的检测和终止机制？

情况：认为任务未完成，失去历史记录，或幻觉遗忘先前的任务而跑偏？

我认为需要设定最大循环轮次，达到该轮次就强制停止，以及终止可以设置final\_answer和无工具调用请求和len=0等多种机制，触发其一就停止。

补充：循环原因还有很多：

* 工具持续报错、超时、限流、权限拒绝。

* 工具返回空结果或格式不对。

* 模型重复相同动作、相同参数。

* 目标模糊，模型无法判断是否完成。

* 环境状态没变化，但模型以为变了。

* 上下文超长导致遗忘前面已经做过。

* 多 Agent 互相等待，死锁。

* 幻觉出不存在的新任务，跑偏。

检测机制：

* 重复动作检测：相同动作+参数出现 N 次。

* 状态哈希：环境状态未变。

* 无进展检测：关键指标不改善。

* 成本/时间/轮数预算。

* 工具错误率阈值。

终止机制：

* 最大轮次。

* 超时/超预算。

* 重复检测触发。

* 无工具调用或 `final_answer`。

* 降级到工作流。

* 请求人工接管。

* 返回部分结果+错误报告。

## 护栏部分提到了工具风险评级。如果一个工具在大多数情况下是低风险的，但在特定参数组合下变为高风险（如 delete\_file 删除普通文件 vs 删除系统文件），你会如何设计动态风险评估？

默认为低风险，但需要找出哪些组合下可能是高风险，将其标记出来，单独作为高风险操作。

补充：

* 实现上通常用一个**策略引擎**：

  * **参数级规则**：比如 `delete_file(path)`，如果 `path` 匹配 `/tmp/*`，低风险；如果匹配 `/etc/*` 或 `C:\Windows\*`，高风险。

  * **组合级规则**：比如 `transfer_money(amount, to)`，如果 `amount > 10000` 且 `to` 不在白名单，高风险。

  * **上下文级规则**：如果当前用户是新注册用户，或者当前会话处于敏感时期，所有写操作都升级为高风险。

* 高风险操作应该触发**人工确认**（Human-in-the-loop），而不是直接拒绝。这样既安全，又不阻断正常业务。

## 人工干预机制要求 Agent 能“优雅地移交控制”。但在实践中，用户可能不在线、响应很慢、或者给出模糊的指令。此时 Agent 应该怎么办？

我觉得应该先停止工作，如果用户不在线，有提醒机制的情况下先提醒用户，否则就先待机等待，避免浪费token，响应很慢同上。如果指令不够清晰，无法理解的情况下，应该先说明自己的理解，告知用户，请用户确认或纠正，而不是尝试说明自己哪里不清楚，很可能因为幻觉问题而略过。

补充：其他策略：

1. **超时机制**：如果用户 N 分钟无响应，自动回滚到上一个稳定状态，并保存进度，等用户回来再继续。
2. **预设选项**：对于模糊指令，不要只给开放式提问，而是给出几个可能的理解选项，让用户点选，降低用户输入成本。
3. **升级人工**：如果 Agent 无法理解，且用户也不在线，可以转交人工客服，并附上 Agent 的理解和已尝试的操作，方便人工快速接手。
   4.**安全默认**：在不确定的情况下，默认选择最安全、最保守的操作，而不是最激进的操作。

## 引言指出“好的设计原则应该穿越模型的迭代周期”，但实现这些原则的具体工程手段可能会随模型能力进步而过时。试举一个这样的 Agent 工程手段，并说明理由。

我觉得CoT本身就是一个例子，一开始只是通过提示词说明“step by step”，后期优化为模型自己的能力，也就是CoT思维链，这并不会导致思维链这个设计成为无用品，而是使其内化，利于agent在其基础上继续发展。

补充：其他类似例子：

1. **工具调用**：早期靠 ReAct 提示词让模型输出特定格式来调用工具，现在模型原生支持 Function Calling，提示词工程被内化。
2. **记忆管理**：早期靠手动维护向量数据库和检索逻辑，现在模型上下文窗口越来越大，甚至有了原生记忆功能，外部 RAG 的必要性在部分场景下降低。
3. **规划**：早期靠“先写计划再执行”的提示词，现在推理模型（如 o1、DeepSeek-R1）原生具备长程规划能力，外部规划器的重要性下降。

* 核心规律：**任何可被模型内化的、重复性的、模式固定的工程手段，最终都会被模型吃掉。但那些涉及安全、权限、确定性编排、多 Agent 协作的 Harness 能力，会长期存在，甚至越来越重要。**
